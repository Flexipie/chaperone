Run many coding agents in lanes, with the process enforced in code

Usage: chaperone [OPTIONS] <COMMAND>

Commands:
  work       Leased work records. Claim an item before working on it, heartbeat while you hold it, hand it off when you stop
  spec       The dispatch spec of a parent issue, versioned. /dispatch writes it, /issue and /ship read it
  check      Check results a fresh session records for a lane: plan check, quality gate, merge verdict, smoke, kept tests and review rounds; and the checks the binary runs itself
  reviews    Daisy's review jobs, as recorded in the ledger. The worker stays in daisy; lanes keep `daisy-cli reviews local` and `reviews get --wait`
  jobs       Recorded daisy jobs
  usage      Token usage per provider message, read from a lane's transcripts
  attention  Interventions on a lane by the orchestrator or the owner
  finding    A lane's review and plan check findings: list them, the lane disputes or accepts one, the owner waives one
  dossier    The agent-only record of an issue key: notes, and one capped read of what the ledger knows about the key. Data for agents, never a gate
  evidence   The evidence store beside the ledger: text a check or a harness session stored, named by its sha256
  overlap    Per file, the open lanes touching it: each lane's newest handoff (changed_files), then the commits on its worktree's HEAD since the merge-base with origin, all git calls within 5 s. Shared files first. Call it before starting work
  stats      R11's lane and cohort numbers, read from the ledger: claim to merge, tokens, peak context, attention, checks and the verdict on the merged head. A number nothing records yet is null, and `missing` names what it needs
  impact     The files that depend on these Rust files, nearest first: module nodes and import edges read with tree-sitter from the worktree, facts cached by content per origin. Each depth says if it is exact or a lower bound; at most 500 files listed
  verify     Run `check run` diff, tests, review and verdict on the lane's commit in that order, under one hold of the lane's run lock (a second run is a conflict, exit 4), stopping at the first step refused or not passed; the verdict runs only after a complete review that leaves no finding blocking. Prints each step and where and why it stopped. Plan and smoke are not steps
  pr         The lane's pull request
  merge      The owner's merge of the lane's PR, as chaperone-ui's Merge: on a YES verdict on --head, the lane ready and GitHub's PR head still --head, `gh pr merge --squash --delete-branch --match-head-commit`, then `pr.merged`, then the done handoff unless the lane's lease is live, when `herdr agent prompt` tells its agent to hand off done. Refused from any session or agent that has held the lane
  pipeline   The pipeline documents this binary runs
  doctor     Check skill and script files against this binary: every chaperone command, flag and value they call, the handoff fields they write and the pipeline version they name. With --repo, also the repo's profile areas and whether this binary's code differs from the repo's origin/main. Any mismatch is a `drift` error (exit 1) listing each with file:line. Reads files and git, never the ledger
  migrate    Create the ledger, or migrate it to this binary's version after a backup. Refuses a file that is not a Chaperone ledger
  install    Write the Claude Code plugin embedded in this binary as a marketplace in the user data dir, replacing what was there, and register it with `claude plugin marketplace add` and `claude plugin install chaperone@chaperone --scope user`. Safe to run again. Never reads the ledger
  uninstall  `claude plugin uninstall` and `claude plugin marketplace remove` for what `install` registered (a refusal of what is not there is reported, not an error), then delete the marketplace directory
  hook       The plugin's Claude Code hook for the lane $CHAPERONE_WORK: reads the hook's JSON on stdin and prints the hook's answer, not an envelope. Nothing outside an open lane on a v20 or newer pipeline; the plugin's shim keeps every failure silent
  help       Print this message or the help of the given subcommand(s)

Options:
      --db <DB>          Path to the ledger (defaults to chaperone/ledger.db in the user data dir)
      --format <FORMAT>  Output format: json is one {ok, data, meta} object; jsonl is one item per line followed by a trailer that is the only line with an `ok` key [default: json] [possible values: json, jsonl]
  -h, --help             Print help
  -V, --version          Print version

Every command prints one {ok, data, meta} object on stdout, or an {ok: false, error, meta} object on stderr. Exit codes: 0 ok, 1 error, 2 usage, 3 schema mismatch, 4 conflict, 5 runtime unavailable. Only `chaperone migrate` creates or migrates the ledger; every other command exits 3 on any other schema version.
